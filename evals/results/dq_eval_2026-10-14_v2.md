## Scoring rules

- Ground truth: workspace.generator.manifests, only batches with known ground truth: the manifested batch dates minus 10-02 and 10-03, which also hold rows the 10-01 run wrote without a manifest. Rows from unmanifested writes (09-14 increment, 10-01 run, 10-09..10-13) are neither hits nor false rejects; they are listed as unknown ground truth.
- Attribution: a key belongs to the first snapshot in which the rule fails it (the generator re-emits keys with their latest values, so a defect carries into later snapshots).
- Customers (full load, current state only): a manifest row counts while the current row still shows its defect, and a failing row in no manifest is a false reject (there is no batch to attribute it to).
- Existing-rule coverage: a defect type an active rule already fails on >= 80% of its manifest rows is covered; proposing it again would be nagging (design v2 section 5), so it is reported but not required for recall.
- Found: a VALIDATED rule fails >= 80% of a type's manifest rows (NULL-key rows by count). Precise: a proposal fails >= 50% of some manifest type on its table, whatever its validation status.
- NULL counts as a failure (like dq.py's HARD rules: coalesce((expr), false)).
